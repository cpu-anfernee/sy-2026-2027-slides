Part II: Chapter 1 — Introduction to Python Algorithms

Chapter 1 Learning Objectives

Following Hetland (2010), Chapter 1 (pp. 1–7), by the end of Week 1 you will be able to:

  1. Define what an algorithm is and distinguish algorithmic efficiency from hardware or language speed.
  2. Explain why studying algorithm design prevents reinventing the wheel and exposes hidden performance traps.
  3. Identify the mathematical and Python prerequisites needed to treat Python as "executable pseudocode."
  4. Empirically measure and contrast linear ($O(n)$) vs. quadratic ($O(n^2)$) scaling in Python.

1.1 What's All This, Then?

Before writing a single line of code, what exactly is an algorithm?

  • Formal Definition: A well-defined, step-by-step computational procedure that transforms a valid input into a desired output in finite time.
  • Recipes vs. Engineering: Like a cooking recipe, an algorithm specifies exact operations—but in computer science, we must also prove correctness and analyze resource scaling (time and memory).
  • Algorithms + Data Structures: Data structures organize information in memory (e.g., hash tables, heaps, graphs); algorithms manipulate those structures efficiently.

Why Algorithm Choice Beats Hardware Speed

A common misconception: "Computers are fast enough now; why worry about efficiency?"

  • Constant Factors vs. Growth Rates: Switching from Python to C might give a $10 \times$–$50 \times$ constant speedup, while buying a faster CPU might give $2 \times$.
  • Asymptotic Dominance: As input size $n$ grows (e.g., $n = 10^6$ records), an $O(n \lg n)$ algorithm in pure Python easily crushes an $O(n^2)$ algorithm written in hand-tuned C!
  • Intractability Wall: For exponential $O(2^n)$ brute-force searches, even a supercomputer stalls at $n \approx 60$ without smarter algorithmic pruning or heuristics.

1.2 Why Are You Here?

Hetland highlights two compelling reasons every software engineer needs algorithm design:

  • 1. Don't Reinvent the Wheel (Problem Recognition): Many real-world business bugs are disguised versions of classic problems (topological sorting, shortest paths, bipartite matching, knapsack). Knowing standard abstractions lets you reuse proven solutions.
  • 2. Look Inside the Black Box: Even when calling built-in libraries (sort(), in, heapq, bisect), knowing their underlying guarantees prevents accidental $O(n^2)$ bottlenecks in production.
  • Knuth's Maxim: "Premature optimization is the root of all evil"—optimize architectural bottlenecks, not micro-syntax!

1.3 Prerequisites & Python as Executable Pseudocode

Why does this course use Python instead of traditional textbook pseudocode?

  • Readable & Concise: Python's indentation, tuple unpacking, list/dict comprehensions, and generators (yield) read almost identically to mathematical pseudocode.
  • Immediately Runnable: Unlike static pseudocode, every listing can be executed, tested against edge cases, and profiled with timeit.
  • Mathematical Toolkit: You only need basic discrete math (sets, functions, summations, logarithms) and comfort reading inductive arguments—which we will review in Weeks 2–4.
  • 2010 vs. Modern Python Note: Hetland (2010) wrote for the Python 2/3 transition; in our labs, we modernize older constructs into clean Python 3.11+ idioms.

Seeing Asymptotic Growth in 12 Lines of Python

Two ways to build a list of $n$ elements—one scales linearly, the other quadratically:

import timeit

def build_append(n: int) -> list[int]:
    nums = []
    for i in range(n):
        nums.append(i)       # O(1) amortized per step -> O(n) total
    return nums

def build_insert_front(n: int) -> list[int]:
    nums = []
    for i in range(n):
        nums.insert(0, i)    # Shifts all existing elements -> O(n^2) total!
    return nums

print("append (n=50_000):", timeit.timeit(lambda: build_append(50_000), number=5))
print("insert (n=50_000):", timeit.timeit(lambda: build_insert_front(50_000), number=5))

Doubling $n$ roughly doubles runtime for build_append, but quadruples ($4 \times$) runtime for build_insert_front!

1.4 What's in This Book: Foundations & Traversal

How the first half of Hetland (2010) builds your analytical and structural toolkit:

  • Chapter 2 — The Basics: Asymptotic notation ($O, \Omega, \Theta$), empirical profiling, graph/tree representations in Python, and data structure "Black Boxes."
  • Chapter 3 — Counting 101: Combinatorics, summations, solving recurrences via substitution and recursion trees, and the Master Theorem.
  • Chapter 4 — Induction, Recursion & Reduction: Designing algorithms inductively, loop invariants, linear-time sorting, and topological sorting.
  • Chapter 5 — Traversal (The Skeleton Key): Depth-First Search (DFS), Breadth-First Search (BFS), Iterative Deepening, and Strongly Connected Components.

1.4 What's in This Book: Paradigms & Hard Problems

How the second half tackles optimization strategies and computational limits:

  • Chapter 6 — Divide, Combine, and Conquer: Balanced recursion trees, binary search / bisect, Merge Sort, Quicksort, Quickselect, and geometric D&C.
  • Chapter 7 — Greed Is Good? Prove It!: Greedy choice proofs ("staying ahead" & exchange arguments), Huffman coding, Kruskal's & Prim's MSTs.
  • Chapter 8 — Tangled Dependencies & Memoization: Dynamic Programming over overlapping subproblem DAGs (LIS, LCS, Edit Distance, Knapsack).
  • Chapters 9–11 — Paths, Flows & Intractability: Dijkstra, Bellman-Ford, $A^*$, Max-Flow/Min-Cut, NP-Completeness reductions, and approximation.

1.5 "If You're Curious" & How to Succeed in SE 2236

Mastering algorithms requires combining theoretical pen-and-paper rigor with hands-on experimentation:

  • Trace by Hand First: Before coding any graph or DP algorithm, draw the subproblem graph or state table on paper for a small input ($n = 4$ or $5$).
  • Benchmark Your Hypotheses: Use timeit to verify whether your empirical growth curve matches your theoretical Big-O prediction.

1.6 Summary of Chapter 1

  1. Algorithms Matter Most: Asymptotic growth rates ($O(n)$ vs. $O(n^2)$ vs. $O(2^n)$) dominate hardware speed and language constant factors as problem sizes scale.
  2. Abstraction & Reuse: Recognizing classic algorithmic problems prevents reinventing the wheel and avoids hidden data-structure traps.
  3. Python as Executable Pseudocode: Python's clean syntax and rich built-in structures let us express, verify, and profile algorithms directly.
  4. Semester Trajectory: Across 18 weeks, we progress from asymptotic analysis and traversal to D&C, Greedy, Dynamic Programming, Flows, and NP-Completeness.
