Part I

Abstract Machine Models

How do we measure an algorithm without tying it to one laptop or CPU?

Formalizing Problems & Input Size

What is a Computational Problem?

Mathematically, a problem is a relation between a set of valid inputs $A$ and acceptable outputs $B$.

  • Problem: The general specification (e.g., Sorting: output has identical elements in non-decreasing order).
  • Problem Instance: One specific input $x \in A$ (e.g., [42, 7, 19, 7]).
  • Algorithm: A finite sequence of step-by-step instructions that transforms any valid instance into an acceptable output in finite time.

Measuring Input Size ($n$)

Computers encode inputs as binary strings (0s and 1s). Input size $n$ is either:

  • The number of items (e.g., $n$ elements in a list, $|V|$ vertices in a graph), OR
  • The number of bits needed to encode the instance in a reasonable base (e.g., binary, not unary 11111...).
Key Insight: Reasonable encodings (binary, decimal, hexadecimal, ASCII) differ only by constant factors—which asymptotic analysis safely ignores!

The Turing Machine (Alan Turing, 1936)

Originally conceived to study the Entscheidungsproblem (whether an algorithm can decide the truth of any mathematical statement).

  • Infinite Tape: Divided into discrete cells, each holding a symbol from a finite alphabet.
  • Read/Write Head: Inspects one cell at a time, writes a new symbol, and moves Left or Right one step.
  • Finite State Control: A finite table of rules:
    "In State 4, if symbol is X → write Y, move Left, switch to State 9."
  • Halting Requirement: A Turing machine that loops forever is a program, not an algorithm.

Tape & Finite Control Sketch

Church-Turing Thesis: Anything computable by any modern supercomputer can be computed by a Turing machine. Great for decidability & NP-completeness, too tedious for fine-grained runtime analysis.

The Random-Access Machine (RAM) Model

Scrolling along a paper tape takes $O(n)$ just to reach memory slot $n$. For algorithm analysis, we use an abstract single-core computer called the RAM Model:

1. Sequential Execution

Instructions execute one after another. No free parallel execution across infinitely many cores.

2. $O(1)$ Primitive Ops

Basic arithmetic (+, -, *, /), comparisons, branches, and direct memory reads/writes take constant time. Complex operations (like sort()) do not.

3. Bounded Word Size

One memory word holds $\Theta(\lg N)$ bits—large enough to address memory, but not infinite (prevents packing an entire array into one integer to "cheat" in $O(1)$).

Python Caveat: Python integers have arbitrary precision! Adding two 1,000,000-digit integers in Python is not $O(1)$—it scales linearly with the number of digits!

Part II

Mastering Asymptotic Notation

How to strip away hardware noise and capture pure algorithmic scaling

Why Growth Rate Crushes Hardware Speed

Suppose you compare two ways to build a list of $n$ items in reverse order:

Algorithm A (Slow Machine + Pure Python):
Appends to the end & reverses once ($\propto n$ steps).
Handicap: Runs 50,000× slower per step than Algorithm B!
Algorithm B (Supercomputer + Optimized C):
Calls nums.insert(0, i) repeatedly ($\propto n^2$ steps).
Advantage: 50,000× faster per elementary operation!

Units Don't Matter Either! Whether you measure time in nanoseconds or Jovian years, and input size in bytes or kilograms of hard drives, constants cancel out!

Input Size ($n$) Slow Python ($\propto n$) Fast C Supercomputer ($\propto n^2$)
$n = 100$ 5.0 sec 0.01 sec (B wins)
$n = 50,000$ 41.6 min 41.6 min (Tie!)
$n = 100,000$ 1.4 hrs 2.8 hrs (A is 2× faster)
$n = 10,000,000$ ~1 minute (scaled) ~1.5 DAYS (2,000× slower!)

Asymptotic notation acts like a mathematical zoom-out lens: it ignores constant multipliers ($c$) and focuses purely on the shape of the curve as $n \to \infty$.

Intuition First: Four Ways to Bound Growth

Think of asymptotic notation as comparing the growth speed of your algorithm's step count $f(n)$ against a clean reference curve $g(n)$ (like $n$, $n \lg n$, or $n^2$) once $n$ becomes large enough:

Symbol Name Analogy Plain-English Meaning
$f(n) \in O(g(n))$ Big-O Speed Limit ($\le$) $f(n)$ grows no faster than $g(n)$ (Asymptotic Upper Bound).
$f(n) \in \Omega(g(n))$ Big-Omega Minimum Speed ($\ge$) $f(n)$ grows at least as fast as $g(n)$ (Asymptotic Lower Bound).
$f(n) \in \Theta(g(n))$ Big-Theta Tight Sandwich ($=$) $f(n)$ grows at the exact same rate as $g(n)$ (Both $O$ and $\Omega$).
$f(n) \in o(g(n))$ Little-o Strictly Slower ($<$) $f(n)$ is completely dominated by $g(n)$ as $n \to \infty$.
Important Notation Note: Technically, $O(g(n))$ is a set of functions, so $f(n) \in O(g(n))$ is the exact statement. By universal convention, computer scientists also write $f(n) = O(g(n))$ — read = as "is in the class", never as symmetric algebraic equality!

Formal Definition: Big-O ($O$)

A function $f(n)$ is in $O(g(n))$ if there exist two positive constants $c > 0$ and $n_0 \in \mathbb{N}$ such that:

$$0 \le f(n) \le c \cdot g(n) \quad \forall\, n \ge n_0$$

  • What is $c$? A constant "stretching factor" (representing faster hardware or lower-level C code) that lets $c \cdot g(n)$ sit above $f(n)$.
  • What is $n_0$? The "warm-up threshold." Before $n_0$, $f(n)$ is allowed to misbehave or be larger. After $n_0$, $c \cdot g(n)$ must win forever.
  • Existential Quantifier ($\exists$): You only need to find one valid pair $(c, n_0)$ to prove Big-O!

Before $n_0$, $f(n) > c \cdot g(n)$ is fine. Past $n_0$, $c \cdot g(n)$ acts as an unbreakable ceiling.

Worked Proof #1: Proving a Big-O Bound

Claim: Prove formally from the definition that $f(n) = 2.4n^2 + 7n + 15 \in O(n^2)$.

Strategy: Bound Every Term by $n^2$

  1. We need constants $c > 0$ and $n_0 \ge 1$ such that:
    $$2.4n^2 + 7n + 15 \le c \cdot n^2 \quad \forall\, n \ge n_0$$
  2. Notice that whenever $n \ge 1$:
    • $2.4n^2 \le 2.4n^2$
    • $7n \le 7n^2$ (since $n \le n^2$ for $n \ge 1$)
    • $15 \le 15n^2$ (since $1 \le n^2$ for $n \ge 1$)
  3. Add the inequalities together for all $n \ge 1$:
    $$2.4n^2 + 7n + 15 \le (2.4 + 7 + 15)n^2 = 24.4n^2$$
Witness Found!
Choose $c = 24.4$ (or $c = 25$) and $n_0 = 1$.
Since $2.4n^2 + 7n + 15 \le 25n^2$ for all $n \ge 1$, we have proved $f(n) \in O(n^2)$. $\blacksquare$
Are $(c, n_0)$ Unique? No!
If we wait until $n_0 = 10$, then:
$7n + 15 = 70 + 15 = 85 \le 0.6n^2$ (since $0.6(100) = 60$, wait at $n_0 = 15$: $7(15)+15 = 120 \le 0.6(225) = 135$).
Thus $(c = 3,\; n_0 = 15)$ is also a valid witness! Increasing $n_0$ lets us shrink $c$.

Worked Proof #2: Disproving a False Bound

Students often ask: "Why can't we just pick a gigantic $c$ (like $c = 10^{100}$) to force $n^2 \in O(n)$?"

Claim: Prove that $f(n) = n^2 \notin O(n)$.

Proof by Contradiction:

  1. Suppose for the sake of contradiction that $n^2 \in O(n)$.
  2. By definition, there must exist fixed constants $c > 0$ and $n_0 \in \mathbb{N}$ such that: $$n^2 \le c \cdot n \quad \text{for all } n \ge n_0$$
  3. Since $n \ge n_0 \ge 1 > 0$, we can divide both sides by $n$: $$n \le c \quad \text{for all } n \ge n_0$$
  4. Contradiction! $c$ is a fixed constant, whereas $n$ grows without bound. Specifically, pick $n^* = \max(n_0, \lfloor c \rfloor + 1)$. Then $n^* \ge n_0$, yet $n^* > c$, violating $n^* \le c$. Therefore, $n^2 \notin O(n)$. $\blacksquare$

Big-Omega ($\Omega$) & Big-Theta ($\Theta$)

Big-Omega (Lower Bound): $f(n) \in \Omega(g(n))$ iff $\exists c > 0, n_0 \in \mathbb{N}$ such that: $$0 \le c \cdot g(n) \le f(n) \quad \forall\, n \ge n_0$$ Inverse Rule: $f(n) \in O(g(n)) \iff g(n) \in \Omega(f(n))$.
Big-Theta (Tight Bound): $\Theta(g(n)) = O(g(n)) \cap \Omega(g(n))$.
$\exists c_1, c_2 > 0$ and $n_0 \in \mathbb{N}$ such that: $$0 \le c_1 \cdot g(n) \le f(n) \le c_2 \cdot g(n) \quad \forall\, n \ge n_0$$
Example: Show $3n^2 + 2n \in \Theta(n^2)$.
For all $n \ge 1$: $\; 3n^2 \le 3n^2 + 2n \le 5n^2$.
Witnesses: $c_1 = 3,\; c_2 = 5,\; n_0 = 1$.

Past $n_0$, $f(n)$ is trapped inside the sandwich between $c_1 g(n)$ and $c_2 g(n)$.

Little-o ($o$) & The Calculus Limit Shortcut

Finding $(c, n_0)$ by hand is great for rigor, but in practice we can quickly compare two smooth positive functions $f(n)$ and $g(n)$ using limits:

$$L = \lim_{n \to \infty} \frac{f(n)}{g(n)}$$

Limit Value $L$ Asymptotic Relationship Example ($f(n)$ vs. $g(n)$)
$L = 0$ $f(n) \in o(g(n))$  (strictly slower; implies $O(g)$) $\lim_{n\to\infty} \frac{n \lg n}{n^2} = 0 \implies n \lg n \in o(n^2)$
$0 < L < \infty$ $f(n) \in \Theta(g(n))$  (identical growth rate) $\lim_{n\to\infty} \frac{5n^2 - 3n}{2n^2 + 9} = \frac{5}{2} \implies \Theta(n^2)$
$L = \infty$ $f(n) \in \omega(g(n))$  (strictly faster; implies $\Omega(g)$) $\lim_{n\to\infty} \frac{2^n}{n^{100}} = \infty \implies 2^n \in \omega(n^{100})$
Subtle Edge Case: If the limit does not exist due to oscillation—e.g., $f(n) = n \cdot (2 + \sin n)$ vs. $g(n) = n$—the limit test is inconclusive, yet $1 \cdot n \le f(n) \le 3 \cdot n$, so $f(n) \in \Theta(n)$ still holds by definition!

Common Asymptotic Complexity Classes

Ordered from slowest growth (best) to fastest growth (worst). Every row strictly dominates all rows above it:

Complexity Name $n = 10$ $n = 1,000$ Typical Algorithm / Python Example
$\Theta(1)$ Constant $1$ $1$ dict / set lookup, array indexing A[i]
$\Theta(\lg n)$ Logarithmic $3.3$ $10$ Binary search (bisect); base of log doesn't matter
$\Theta(n)$ Linear $10$ $1,000$ Single scan over a list, sum(seq), max(seq)
$\Theta(n \lg n)$ Loglinear $33$ $10^4$ Timsort / Merge Sort, optimal comparison sorting ($\Theta(\lg n!)$)
$\Theta(n^2)$ Quadratic $100$ $10^6$ Comparing all pairs, Insertion Sort, nested loops over $n$
$\Theta(n^3)$ Cubic $1,000$ $10^9$ Naïve matrix multiplication, Floyd-Warshall all-pairs shortest paths
$\Omega(2^n)$ Exponential $1,024$ $10^{301}$ Generating all subsets (power set), brute-force SAT
$\Theta(n!)$ Factorial $3.6 \times 10^6$ $4 \times 10^{2567}$ Generating all permutations, brute-force Traveling Salesman

Tractability Boundary: Algorithms in $O(n^k)$ for constant $k > 0$ (including $\Theta(\lg n)$ and $\Theta(n \lg n)$) are called polynomial-time (tractable). Anything in $\Omega(k^n)$ with $k > 1$ hits an exponential wall.

Rules of the Road & Asymptotic Algebra

1. Drop Lower-Order Summands

In a sum, only the fastest-growing term survives:
$$\Theta(n^3 + 50n^2 + 999n + 42) = \Theta(n^3)$$

2. Drop Multiplicative Constants

Constant factors vanish:
$$\Theta(4.2\, n \log_{10} n) = \Theta(n \lg n)$$

3. Keep Your Bounds Tight

While $5n^2 \in O(n^3)$ is technically true, always state the tightest bound: $O(n^2)$ (or $\Theta(n^2)$).

Asymptotic Arithmetic

We often plug $\Theta$ directly into expressions to combine code blocks:

Sequential Addition Rule: $$\Theta(f(n)) + \Theta(g(n)) = \Theta(f(n) + g(n)) = \Theta(\max(f(n), g(n)))$$
Nested Multiplication Rule: $$\Theta(f(n)) \cdot \Theta(g(n)) = \Theta(f(n) \cdot g(n))$$
Logarithm Base Rule:
Since $\log_a n = \frac{\log_b n}{\log_b a}$, changing bases only multiplies by a constant $\frac{1}{\log_b a}$. Thus $\Theta(\log_2 n) = \Theta(\ln n) = \Theta(\log_{10} n)$.

Taking Asymptotics for a Spin: Python Code

1. Sequential + Camouflaged Loops (Add):

nums.append(1)                  
nums.insert(0, 2)               
squares = [x**2 for x in nums]  
total = sum(squares)

2. Independent Input Sizes ($n$ and $m$):

for x in seq1:          # n iterations
    for y in seq2:      # m iterations
        total += x * y

3. Dependent / Triangular Inner Loop:

n = len(seq)
for i in range(n - 1):
    for j in range(i + 1, n):
        s += seq[i] * seq[j]
Careful Counting (Don't Just Multiply!):
Inner loop runs $(n-1) + (n-2) + \dots + 1$ times:
$$\sum_{k=1}^{n-1} k = \frac{n(n-1)}{2} = \frac{1}{2}n^2 - \frac{1}{2}n = \Theta(n^2)$$ Even though the inner loop shrinks, it is still quadratic!

Best, Worst & Average Cases

def sort_w_check(seq):
    n = len(seq)
    for i in range(n - 1):
        if seq[i] > seq[i + 1]:
            break
    else:
        return  # Already sorted!
    seq.sort()  # Runs in Theta(n lg n)
  • Best Case: Input is already sorted → $\Theta(n)$.
  • Worst Case: Input is unsorted → $\Theta(n \lg n)$ (our primary performance guarantee!).
  • Average Case: Expected runtime over random inputs (with an assumed distribution).

Why General Runtime Uses $O$ and $\Omega$, Not $\Theta$!

What is the running time of sort_w_check(seq) across all possible inputs of size $n$?

  • It is NOT $\Theta(n \lg n)$ (fails on sorted inputs).
  • It is NOT $\Theta(n)$ (fails on unsorted inputs).
  • Because different inputs of size $n$ produce different growth orders, no single $\Theta$ bound exists!

Solution: Bound it from above with $O(n \lg n)$ and from below with $\Omega(n)$.

Part III

Python "Black Boxes" & Hidden Traps

What CPython actually does behind clean syntax

Inside Python's Core Data Structures

Type Under-the-Hood Structure $O(1)$ Operations $O(n)$ Operations
list Dynamic Array (contiguous block of object pointers with geometric over-allocation) L[i], L[i] = x, len(L), L.pop(), L.append(x) (amortized) L.insert(0, x), L.pop(0), x in L, L.remove(x)
dict Open-Addressed Hash Table (computes hash(key) to jump directly to a slot) d[k], d[k] = v, k in d, del d[k] (expected) Worst-case hash collision storm (rare in practice)
set Hash Table of keys without values x in s, s.add(x), s.remove(x) (expected) Iterating all elements, set copy
Why is list.append(x) $O(1)$ amortized? When the contiguous array fills up, CPython allocates a larger buffer (~1.125× bigger) and copies all $n$ pointers in $\Theta(n)$ time. Because resizing happens exponentially rarely, the average cost per append across $n$ operations is $\Theta(1)$!

Hidden Quadratic Traps & Floating-Point Pitfalls

Hidden Squares ($O(n^2)$ in Disguise)

# TRAP 1: Membership test in a list loop -> O(n^2)
seen = []
for item in data:        # O(n)
    if item not in seen: # O(n) linear scan!
        seen.append(item)
# FIX: Use seen = set() -> O(1) lookup -> O(n) total!

# TRAP 2: Repeated string concatenation -> O(n^2)
out = ""
for chunk in chunks:
    out += chunk  # Copies entire string each step!
# FIX: out = "".join(chunks) -> O(n) total!

Tip: Need fast front-insert/pop? Use collections.deque ($O(1)$ at both ends).

IEEE 754 Floating-Point Precision

>>> 0.1 + 0.2 == 0.3
False
>>> 0.1 + 0.2
0.30000000000000004
Why? Binary floating-point (64-bit IEEE 754) cannot represent base-10 fractions like $1/10$ or $1/5$ finitely, introducing rounding error ($\approx 10^{-16}$).
  • Never test floats with ==; use math.isclose(a, b).
  • Beware catastrophic cancellation when subtracting two nearly equal floats.
  • Use decimal.Decimal or fractions.Fraction for exact arithmetic.

Part IV

Experimental Algorithmics

Validating theory with disciplined empirical measurements

Measuring Real Performance (Tips 1–3)

Tip 1: Don't Over-Optimize

Algorithm design cuts asymptotic complexity; algorithm engineering trims constant factors.

"When in doubt, use brute force." — Ken Thompson. Write clear code first; optimize only if needed.

Tip 2: Use timeit Safely

import timeit
timeit.timeit("sum(range(100))",
              number=10000)

Mutation Trap!

timeit runs your snippet thousands of times. Timing L.sort() sorts L on run #1, making runs #2..#10,000 artificially fast on an already-sorted list!

Tip 3: Profile with cProfile & trace

import cProfile
cProfile.run("main()")

Never guess bottlenecks! cProfile measures exact call counts and cumulative seconds per function. Use Python's trace module to count exact statement executions.

Scientific Rigor & Refutable Hypotheses (Tips 4–6)

Tip 4: Visualize Scaling & Variance

Plot runtime $T(n)$ vs. input size $n$ (and log-log plots where slope $k$ reveals $\Theta(n^k)$!), alongside box plots to expose OS/GC jitter.

Tip 5: Beware Statistical Traps

  • Random Jitter: Small timing differences may just be background OS noise.
  • Multiple Comparisons: Comparing 20 variants creates $\binom{20}{2} = 190$ pairs—one will look "faster" purely by luck.
  • Generalization: Document Python version, CPU, and input distribution.

Tip 6: You Can't Prove Big-O by Experiment!

Asymptotics describe $n \to \infty$, whereas experiments are always finite.

How to Test Scientifically:

  1. Formulate a refutable (falsifiable) bound from preliminary data:
    "Hypothesis: $T(n) \le 0.24n^2 + 0.1n + 0.03$ sec on my machine."
  2. Stress-test with adversarial inputs and larger $n$ to try to break the inequality.
  3. Surviving repeated attempts empirically supports your $\Theta(n^2)$ model!
